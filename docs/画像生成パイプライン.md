# fal.ai × GitHub Actions 大量画像生成パイプライン 手順書

このリポジトリでマンガ115見開きを生成したときの仕組みのまとめ。
**別のプロジェクトを担当するAIアシスタントに、このファイルを渡せばそのまま再現できる**ことを目的に書いてある。

## 0. 結論(何をどうしたら速くなったか)

最初は「1枚ずつ workflow_dispatch → push を待つ → 次を投入」でやっていて、1枚あたり
待ち時間込みで2〜3分かかっていた。最終形はこう:

1. **原稿(ネームJSON)→ 生成プロンプトの変換をスクリプトで自動化**(手書きをやめる)
2. 変換結果を **JSONL(1行=画像1枚)** としてリポジトリにコミット
3. **「JSONLを渡すと章まるごと順に生成して最後に1回だけcommit/pushするワークフロー」** を用意
4. そのワークフローを **章ごとに並列で走らせる**(章内は直列、章間は並列)

これで46枚を約20分・失敗ゼロで生成できた(1枚ずつ方式なら2時間コース)。
ポイントは「並列にしたこと」そのものより、**push衝突をなくした(章1回)**ことと
**プロンプト作成を機械化した**こと。

## 1. 前提

- 静的サイトのリポジトリ(GitHub)。画像は `manga/img/chNN/spreadNN.jpg` のような規則的パスに置く
- fal.ai のAPIキーを **GitHub Secrets** に `FAL_KEY` として登録(チャットやリポジトリには絶対に書かない)
- 実行環境からfal.aiに直接アクセスできない場合でも、GitHub Actionsのランナーからは叩ける
  (このプロジェクトはまさにそのパターン。ローカルのネットワーク制限を Actions で迂回した)
- モデルは `fal-ai/nano-banana-pro`(テキスト→画像)と `fal-ai/nano-banana-pro/edit`
  (参照画像つき生成。**キャラの一貫性が必要なら必ずこちら**)。単価はおよそ$0.15〜0.2/枚

## 2. 構成ファイル

```
tools/build_manga_prompts.py   原稿JSON → プロンプトJSONL 変換スクリプト
prompts/chNN.jsonl             生成ジョブの一覧(1行=1枚)
.github/workflows/genimg.yml   1枚だけ生成する単発ワークフロー(修正・差し替え用)
.github/workflows/genbatch.yml JSONLを順に処理するバッチワークフロー(本命)
```

### 2.1 JSONLの形式(1行=1ジョブ)

```json
{"path": "manga/img/ch06/spread03.jpg",
 "prompt": "(英語の生成指示。日本語の台詞はそのまま埋め込む)",
 "aspect_ratio": "16:9",
 "image_urls": ["https://raw.githubusercontent.com/<owner>/<repo>/<branch>/…/参照1.jpg", "…/参照2.jpg"]}
```

- `image_urls` は **rawgithubusercontent のURL**。リポジトリにコミット済みの画像を
  そのまま参照画像にできる(=デザインシートや既存ページを「お手本」にできる)
- 参照は2〜3枚まで。多すぎると効かない

### 2.2 バッチワークフローの本体(genbatch.yml の要点)

```yaml
on:
  workflow_dispatch:
    inputs:
      list:  { description: 'プロンプトJSONLのパス', required: true, type: string }
      model: { default: 'fal-ai/nano-banana-pro/edit', type: string }
jobs:
  generate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: |
          while IFS= read -r line; do
            path=$(echo "$line" | jq -r .path)
            [ -f "$path" ] && continue          # ←既存ファイルはスキップ(再開・部分再生成の要)
            body=$(echo "$line" | jq '{prompt:.prompt, num_images:1, aspect_ratio:.aspect_ratio, image_urls:.image_urls}')
            resp=$(curl -sS -X POST "https://fal.run/$MODEL" \
              -H "Authorization: Key $FAL_KEY" -H "Content-Type: application/json" -d "$body")
            url=$(echo "$resp" | jq -r '.images[0].url // empty')
            [ -z "$url" ] && { echo "::warning::失敗: $path"; continue; }   # ←1枚失敗しても止めない
            mkdir -p "$(dirname "$path")" && curl -sS -o "$path" "$url"
          done < "$LIST"
      - run: |  # 最後に1回だけコミット。並列ラン対策でリトライ+ランダム待機
          git add manga/img || true
          git diff --cached --quiet || git commit -m "画像バッチ生成: $LIST"
          for i in 1 2 3 4 5 6 7 8; do git push && break || { git pull --rebase; sleep $((RANDOM % 8 + 2)); }; done
```

## 3. 運用手順

1. 原稿(構造化されたネームJSON等)を `docs/` に置く
2. 変換スクリプトを回して `prompts/chNN.jsonl` を生成・コミット
3. 章ごとに `workflow_dispatch` で genbatch を起動(章の数だけ並列に投げてよい)
4. 完了検知は「最終ページのファイルがリモートに存在するか」をポーリング:
   `git fetch && git cat-file -e FETCH_HEAD:manga/img/ch10/spread14.jpg`
5. `git pull` して枚数と0バイトファイルの有無だけ機械チェック
   (`find … -size -50k` で怪しいファイルを検出)

### 部分的に作り直したいとき

- **1枚だけ**: 単発ワークフロー(genimg.yml)に修正プロンプトを渡して上書き生成
- **複数枚**: 該当ファイルを `git rm` して genbatch を再実行
  (既存スキップのおかげで、消したページだけが再生成される)

## 4. プロンプト自動生成のコツ(変換スクリプトの設計)

原稿がコマ単位の構造化データなら、プロンプトは完全に機械生成できる。

- **レイアウトを固定文で宣言**: 「16:9横長、右綴じ、右ページ上中下→左ページ上中下の6コマ、
  白い溝」— 全ページ共通の前文にする
- **キャラ辞書**: キャラ名→英語の容姿記述(髪・耳・瞳・服)の辞書を1つ持ち、
  そのページに登場するキャラの分だけ前文に注入する
- **参照画像の自動選択**: キャラ→参照URLの優先表を持ち、登場キャラから上位2〜3枚を選ぶ。
  デザインシート > そのキャラがよく写った既存ページ > 画風アンカー の順
- **台詞は原文をそのまま**: 「All text in Japanese, copied EXACTLY character-for-character」
  と宣言した上で、台詞・ナレーションを原文のまま埋め込む。
  さらに「draw ONLY the text listed below(指定以外の文字を描くな)」で余計な吹き出しを抑止
- **品質ガードを全ページに注入**(失敗から学んだ定型文):
  - 獣人化防止: 「all characters are HUMAN-shaped people with animal ears (kemonomimi);
    NEVER draw them as real animals」— 「狐と兎が〜」のような内容のページで特に効く
  - 画風固定: 「crisp clean Japanese anime cel-shading, NOT painterly」—
    "painterly" と書くと水彩に流れる。書かないこと
  - 年齢固定: 加齢描写が要らないのに "older" と書くと老けるので書かない

## 5. ハマりどころ(実際に踏んだもの)

| 症状 | 原因と対策 |
|---|---|
| pushが衝突して失敗 | 並列ランが同時にpushするため。**コミットは章1回**+リトライ8回×ランダム待機 |
| 日本語が微妙に化ける(誤字・重複) | 生成モデルの限界。長文ほど化けるので**台詞は短めに分割**。重要ページのみ再生成 |
| キャラが動物の顔になる | 内容に引っ張られる。ガード文(上記)+人間顔の参照画像を渡す |
| 画風がページごとにブレる | 直前の生成ページを参照にすると**ズレが連鎖**する。参照は常に「基準ページ(1〜2章)+デザインシート」に固定 |
| fal側で生成拒否(空レスポンス) | 血・死などの単語で安全フィルタに触れることがある。**婉曲表現に書き換えて再投入**(例: dying→wounded) |
| 手動エンコードした\uXXXXの誤字 | 漢字をエスケープで書くと打ち間違える(椿→椰 等)。**生の日本語で書く**か機械生成にする |
| GitHub Webの「Rename」で画像が壊れる | 既知の罠。**リネームはWeb UIでやらない**。git mv するか、正しい名前で上げ直す |
| workflow_dispatchのchoice型input | 選択肢外の値で422になる。モデルIDは `type: string` にしておく |

## 6. コスト管理

- 1枚 ≒ $0.15〜0.2(nano-banana-pro/edit)。**投入前に枚数×単価を報告**してから回す
- 失敗・キャンセル分も課金される場合がある。正確な額はfalのダッシュボード(Billing)で確認
- 参考実績: 全10章115見開き+表紙9枚+デザインシート7枚+再生成 ≒ $25〜30

## 7. 他プロジェクトへの移植チェックリスト

- [ ] `FAL_KEY` をSecretsに登録(キーは絶対に平文で扱わない)
- [ ] 出力パスの命名規則を決める(既存スキップとポーリングの前提になる)
- [ ] 原稿を構造化する(コマ/カット単位のJSONが理想。なければまず原稿の構造化から)
- [ ] キャラ辞書と参照画像の優先表を作る(デザインシートを最初に生成しておくと安定)
- [ ] genimg.yml(単発)→ 動作確認 → genbatch.yml(一括)の順で導入
- [ ] 品質ガード文をプロンプト生成器に組み込む
